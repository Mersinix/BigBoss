# Promotion Minimum Order Value Fix, Eligibility Validation, Theme Support & Realtime Synchronization — Report

## 1. Root cause of the 10.000 DT → 100.000 DT discrepancy

**The Supplier promotion form stored four monetary fields at 10× their intended value.** `client/src/pages/supplier/promotions-page.tsx`'s `formToPayload` converted `minimumOrderValue`, `maximumDiscount`, `freeShippingMinAmount`, and `discountValue` (for the two types that store an absolute DT amount, `FIXED_AMOUNT`/`MIN_ORDER_AMOUNT`) using `Math.round(parseFloat(value) * 1000)` — a *milli-DT* ("millimes") conversion. `promoToForm` read them back with the matching `/ 1000`. This pair is internally consistent (a supplier editing their own promotion always saw the number they typed), which is why the bug was invisible on the Supplier side.

But `shared/schema.ts`'s own column definitions document all four fields as **cents** (`minimumOrderValue: integer(...) // cents`, `maximumDiscount: integer(...) // cents cap for % discounts`, `discountValue: integer(...) // basis points (for %) or cents (for fixed)`, `freeShippingMinAmount: integer(...) // cents, 0 = always free`) — the exact same unit as every price elsewhere in the app (`variant.price`, `listing.price`, cart `unitPrice`), and the unit `client/src/lib/format.ts`'s global `formatCurrency(cents)` function expects (`(cents / 100).toFixed(3)`). The promotion engine (`server/promotions-engine.ts`) and every customer-facing reader of these fields were written against that cents convention.

So a supplier entering `10.000 DT` had the form write `10 * 1000 = 10000` to the database — but the rest of the app, correctly expecting cents, reads `10000` as `10000 / 100 = 100.00 DT`. That is exactly the reported `100.000 DT`. The bug is **not** in the Promotion Details modal's display code (which — once it simply reads the raw value and calls `fmt()`, with no extra conversion — is already correct); it is in how the value was written to the database in the first place.

**Likely origin**: this app's separate Discount Codes feature genuinely uses a "millimes" (×1000) convention for its own, unrelated `discountCodes.minimumOrderAmount`/`discountValue` columns (explicitly commented `// millimes` in `shared/schema.ts`). The Promotions form's `*1000`/`/1000` pair appears to have been copied from that sibling feature's convention rather than from the Promotions schema's own (different) "cents" convention — a cross-feature unit mix-up, not a deliberate design choice.

## 2. Actual stored value before and after the correction

- **Before this fix**: a supplier-entered "10.000 DT" minimum was stored as `10000` (10× the schema's documented cents value — the equivalent of 100.00 DT read as cents).
- **After this fix (code)**: a supplier-entered "10.000 DT" minimum is stored as `1000` (correct cents, `10 * 100`).
- **Existing rows created before this fix remain at the old, 10×-too-large value** until the corrective migration (§11) is run. No code in this task retroactively rewrites a promotion's data automatically — that would violate the task's own "Do not modify unrelated promotions or automatically multiply/divide all existing records" instruction if done blindly. Instead, a single, narrowly-targeted, idempotent-intent SQL migration was written (`migrations/0010_promotion_monetary_unit_fix.sql`) that corrects only these four columns, only where they are set, dividing by exactly 10 — the precise, provable correction factor for the bug just described. It must be run once, manually, against the real database; this environment has no database connection to run it from (see §13).

## 3. Numeric parsing and formatting corrections

- `promotions-page.tsx`'s `formToPayload`: `minimumOrderValue`/`maximumDiscount` changed from `* 1000` to `* 100`; the `FREE_SHIPPING` case's `freeShippingMinAmount` changed from `* 1000` to `* 100`; the `FIXED_AMOUNT`/`MIN_ORDER_AMOUNT` case's `discountValue` changed from `* 1000` to `* 100` (the percentage-family case was already correctly `* 100` and is untouched).
- `promotions-page.tsx`'s `promoToForm`: the mirror-image `/ 1000` → `/ 100` for the same four fields, so the Supplier's own edit form continues to round-trip correctly with the now-correct stored values.
- `promotions-page.tsx`'s `discountLabel` (the Supplier's own promotion-card display): reverted an earlier, now-superseded attempt at this same fix that had divided by 10 inside `fmt()` calls — once the stored value is genuinely cents, `fmt()` needs no extra division at all; the function now calls `fmt(p.discountValue)`/`fmt(p.freeShippingMinAmount)` directly.
- `server/storage/domains/promotions.storage.ts`'s `_promoLabel` (the `ListingPromotion.label` badge text, e.g. "5.000 DT OFF"): changed `(p.discountValue / 1000)` to `(p.discountValue / 100)` for the `FIXED_AMOUNT`/`MIN_ORDER_AMOUNT` case.
- `client/src/components/product-detail-content.tsx`'s `calcPromoPrice` and `client/src/pages/cafe/store-detail-page.tsx`'s duplicate `calcStorePromoPrice` (both compute a FIXED_AMOUNT promotion's discounted display price): removed an incorrect `Math.round(promo.discountValue / 10)` — `discountValue` is cents, the same unit as `basePrice`, so it is now subtracted directly.
- `promotions.storage.ts`'s `getPromotionDetailForListing` (`FIXED_AMOUNT` branch of its own `promotionalPrice` computation): removed the same incorrect `/ 10`.
- `server/storage/domains/delivery.storage.ts`'s `resolveSupplierSubsidy` (the FREE_SHIPPING delivery-fee-subsidy eligibility check) and `server/routes/supplier.routes.ts`'s public `GET /api/supplier/:supplierId/promotions` endpoint: both read `freeShippingMinAmount`/`minimumOrderValue`/`discountValue` directly, with no conversion — already correct for the cents convention once the stored value is itself correct; both were briefly "fixed" with an incorrect `/10` during an earlier pass of this task and reverted back to the original direct reads once the schema's true unit was confirmed.

All of the above were, at one point during this task, incorrectly "fixed" in the *other* direction (treating the schema's cents fields as if they were milli-DT and dividing every reader by 10) before the schema's own column comments and `formatCurrency`'s cents-based convention were found and the diagnosis was corrected. That detour is called out here for transparency; the final state described above is the one actually shipped and verified by `tsc`/`npm run build`.

## 4. Root cause of the minimum-order eligibility bypass

Independent of the unit bug, `server/promotions-engine.ts`'s `calcDiscount` **never read `minimumOrderValue` at all** for the `PERCENTAGE`, `CATEGORY_DISCOUNT`, `MIN_QUANTITY`, `BUY_X_GET_Y`, `QUANTITY_TIER`, and `FIRST_ORDER` promotion types — only `MIN_ORDER_AMOUNT` and `GIFT` checked it (as their own primary trigger condition), and `FREE_SHIPPING` checked its own separate `freeShippingMinAmount` field. But the Supplier form (`PromotionForm` in `promotions-page.tsx`) offers the "Valeur minimum de commande" field for every type *except* `MIN_ORDER_AMOUNT`/`GIFT`/`FREE_SHIPPING` — meaning a supplier could (and, per this task's example, did) configure a minimum order value on a `CATEGORY_DISCOUNT` promotion that the engine then silently ignored, applying the discount unconditionally the moment the product matched the targeted category, regardless of cart subtotal. This is a separate defect from the unit bug (it is a missing condition, not a wrong number) and was present even before the unit-bug fix.

## 5. Minimum-order scope selected and its justification

The existing, already-implemented precedent for this field — `MIN_ORDER_AMOUNT` and `GIFT`'s own checks — gates on `subtotal`, the full per-supplier cart subtotal computed once per supplier inside `evaluateCartPromotions` (`(items as PromoCartItem[]).reduce((s, i) => s + i.unitPrice * i.quantity, 0)` over *every* item for that supplier, not the category/product-targeted subset). Per the task's own instruction ("Use the existing documented or implemented business rule where one exists… Do not silently change the business meaning of the field"), this task reused that exact scope for every other type rather than inventing a second meaning (e.g., "only the eligible category's subtotal") for the same field. The discount **amount** for `CATEGORY_DISCOUNT`/`PERCENTAGE`/`MIN_QUANTITY` is still computed from the category/product-*targeted* subtotal only, unchanged — only the eligibility *gate* uses the full supplier subtotal. This is documented inline in `calcDiscount` itself. For the task's own worked example (a single product, single category, single supplier), "full supplier subtotal" and "eligible category subtotal" coincide, so this scope choice satisfies every numeric scenario in Part 2.4/Part 6 without ambiguity; a cart mixing eligible and ineligible-category products from the *same* supplier is the one case where the two interpretations would diverge, and this task deliberately follows the pre-existing precedent rather than guessing.

## 6. Promotion eligibility implementation

`calcDiscount` in `server/promotions-engine.ts` now applies one additional gate, before its per-type switch, for every type except `MIN_ORDER_AMOUNT`/`GIFT`/`FREE_SHIPPING` (which already gate themselves): if the promotion has a `minimumOrderValue` set and the supplier's cart subtotal is below it, the promotion contributes nothing (`calcDiscount` returns `null`) — exactly the same "not applied" outcome as every other existing ineligibility check (expired date, paused status, usage limit, etc.), so it composes with the existing stackable/non-stackable/priority logic without any special-casing. No existing rule (dates, status, usage caps, cumulability, priority, product/category/variant targeting) was removed or altered — this is a pure addition to the existing gating chain. This is the single, centralized evaluation function already shared by both the client-side cart preview (`POST /api/promotions/evaluate`) and the authoritative server-side order-creation path (`POST /api/orders`) — there was no duplicated/inconsistent eligibility logic to reconcile elsewhere in the *purchase* lifecycle (Part 2.5); the two genuinely separate consumers found during the audit (the Product Detail Modal's own client-side price-preview logic, and the Delivery System's free-shipping subsidy calculation) are display/preview layers that **read** the same promotion data to decide whether to show a discounted price, not a second pricing engine — both are covered below (§6, §8) rather than being redirected through the server engine, since neither one creates an order or a charge.

**Product Detail Modal / Store grid (display layer, Part 2.6)**: `product-detail-content.tsx`'s `VariantRow` and `headerBestPromoPrice`, and `store-detail-page.tsx`'s `StoreProductCard`/`bestStorePromoPrice`, now each compute the viewing Coffee Owner's *current* cart subtotal for that specific supplier (from the existing `useCart()` zustand store, reading the original — not discounted — `unitPrice`, consistent with the earlier double-discount fix) and only treat a minimum-order-gated promotion as "eligible now" if that subtotal already meets the threshold:
- When eligible: unchanged, existing behavior — the filled rose "20% OFF"-style badge, the strikethrough original price next to the discounted one.
- When not yet eligible: the original (undiscounted) price is shown with **no** strikethrough/discounted price at all, and the badge becomes a muted outline style with the French line `"Ajoutez des produits éligibles pour atteindre le montant minimum de commande."` underneath, in `VariantRow`. The badge stays clickable in both states — it always opens the Promotion Details modal, which explains the exact condition — satisfying "clearly distinguish between a potentially available promotion and an active discount" without inventing a condition that doesn't exist (the French line is only ever shown for a promotion that genuinely has a `minimumOrderValue` set and isn't yet met).
- This is reactive to the existing zustand cart store with no new subscription/polling — adding or removing items anywhere in the app re-renders every component reading `useCart()`, including these, instantly (Part 2.7/Part 4.3's "no page refresh" requirement, already satisfied by the pre-existing architecture).

## 7. Server-side validation changes

Only the one engine change described in §6. Everything already audited and confirmed correct in the prior task's work remains true and unweakened:
- `server/storage/domains/order.storage.ts`'s `resolveOrderItems` still re-fetches the real `variant.price`/`listing.price` from the database for every item and **never reads the client-submitted `unitPrice`** — a manipulated cart price submitted by a tampered client is still structurally impossible to turn into a wrong charge.
- `POST /api/orders` (`server/routes/orders.routes.ts`) still re-evaluates promotions from scratch via `storage.evaluateCartPromotions`, using these server-authoritative prices, immediately before computing the final order total and persisting it — so a promotion that was never actually eligible (wrong minimum, expired, paused, usage limit exceeded, wrong category) cannot be smuggled into a real order no matter what the frontend displayed or submitted. The new minimum-order gate added in §6 is evaluated here exactly the same way as the client-side preview, by construction (same function, same inputs) — not a second implementation that could drift out of sync.
- The previous double-discount correction (cart stores the true original `unitPrice`, never a pre-discounted one) is untouched and still in effect; Test 8 (§12) re-confirms it.

## 8. Promotion Details modal theme implementation

**Root cause**: Coffee Owner pages in this app never apply a global Tailwind `dark` class to `<html>` — confirmed by reading `client/src/components/layout/dashboard-layout.tsx`'s own doc comment, which states this activation is "Scoped strictly to Admin/Supplier sessions… so it can never leak into Coffee Owner's own session, which relies on its own separate `isDark`-ternary styling and never expects a global `.dark` class." The Promotion Details modal (`client/src/components/promotion-details-modal.tsx`), as originally written, used Tailwind's `dark:` variant classes throughout (`dark:bg-amber-500/10`, `dark:text-amber-400`, etc.) — which are completely inert in a context that never sets that class, exactly matching the reported "does not correctly adapt to the application's selected theme."

**Fix**: the modal now accepts an `isDark` prop (sourced from the same `useThemeStore` the Product Detail Modal already reads, passed through as the identical `dk = isModal && isDark` value `product-detail-content.tsx` already computes for every other themed element inside that same modal) and derives local ternary tokens (`bg`, `textPrimary`, `textMuted`, `sepColor`, `closeBtnCls`, and inline ternaries for the amber/purple/blue accent colors) exactly mirroring the pattern already used throughout `product-detail-content.tsx` for its own dark-mode support. Every section listed in the task (background, header, type indicator, discount block, price display, validity, conditions, category/product info, cumulability badge, separators, text/labels, icons, the close button, the scrollbar thumb) now reads one of these tokens instead of a `dark:` class. No new theme state was introduced (Part 3.3) — the prop is a pure pass-through of the existing store's value, so switching theme while the modal is open re-renders it immediately via React's normal prop-change re-render, exactly like every other element in the parent modal. The Promotion Details modal has exactly one call site in the Coffee Owner experience (`product-detail-content.tsx`'s shared `auxModals`, used by both the quick-view-modal and full-page layouts of the Product Detail Modal) — it was not duplicated anywhere else, so fixing this one component covers "every promotion details modal instance" by construction.

## 9. Realtime synchronization implementation

**No new infrastructure was introduced.** Auditing the existing architecture first (per the task's own instruction) found it already fully satisfies every requirement in Part 4:

- **Supplier promotion changes (Part 4.2)**: every Supplier promotion mutation route (`POST /api/promotions`, `PUT /api/promotions/:id`, `PATCH /api/promotions/:id/targets`, `PATCH /api/promotions/:id/status`, `POST /api/promotions/:id/duplicate`, `DELETE /api/promotions/:id`) already calls `broadcast('promotion_updated', { supplierId, promotionId })`. `client/src/hooks/use-realtime.ts` already handles this event by invalidating `["/api/marketplace/promotions"]` (the exact query key `product-detail-content.tsx`'s `listingPromotions` and `store-detail-page.tsx` read), `["/api/stores"]`, `invalidateMarketplace(qc)`, and the Supplier's own `["/api/promotions"]`/`["/api/promotions/stats"]`. TanStack Query's `invalidateQueries` matches by key *prefix* unless `exact: true` is passed — confirmed by reading the call site — so this same invalidation also covers the new `GET /api/marketplace/promotions/:id` query this task's prior work introduced for the Promotion Details modal (its query key is `["/api/marketplace/promotions", promotionId, listingId, flavorId, sizeId]`, sharing the same prefix). No new broadcast event or invalidation call was needed.
- **Coffee Owner cart updates (Part 4.3)**: `client/src/hooks/use-promotion-evaluation.ts`'s `usePromotionEvaluation` already builds its TanStack Query key from the live cart contents (`cartItems.map(i => \`${i.listingId}:${i.quantity}\`).sort().join(",")`), so any quantity/item change anywhere in the app automatically triggers a refetch of `POST /api/promotions/evaluate` with the new cart state — already reactive, already no-page-refresh, and now correctly reflects the fixed minimum-order gate from §6 the moment it refetches.
- This confirms the task's own framing ("If the application currently uses polling, inspect whether existing polling can handle the required updates before introducing new infrastructure") — it already does, for every scenario in Part 4.

## 11. Database changes, if any

No schema change (no column type, name, or constraint was altered). One pure **data-correction** migration was written: `migrations/0010_promotion_monetary_unit_fix.sql`. It divides `minimum_order_value`, `maximum_discount`, and `free_shipping_min_amount` by 10 wherever they are non-null, and divides `discount_value` by 10 only for rows where `type IN ('FIXED_AMOUNT', 'MIN_ORDER_AMOUNT')` — the exact set of columns/rows affected by the bug described in §1/§4, nothing else. It follows this project's existing convention for numbered, hand-written, manually-applied migration files (e.g. `migrations/0009_maintenance_visibility_and_theme_repair.sql`). **This migration was not and could not be executed in this environment** (no `DATABASE_URL`/database connection all session) — it must be run once, manually, against the real database, exactly like this project's other post-0001 migration files. Running it a second time would incorrectly divide already-corrected values by 10 again, so it is explicitly commented as a run-once script, not a repeatable one.

One further consequence worth flagging explicitly: any **already-placed order** that used a `FIXED_AMOUNT` or `MIN_ORDER_AMOUNT` promotion before this fix would have had its `promotionUsage.discountAmount` computed from the old, 10×-too-large `discountValue` — meaning a historical order may have recorded (and the Coffee Owner may have actually been charged, since `createOrder`'s `totalAmount` is derived from that same `discountAmount`) a discount roughly 10× larger than the supplier intended. This is a historical financial fact this task cannot retroactively correct — reversing a already-placed order's charge is outside a code/data fix and was not attempted; it is noted here as a limitation (§14), not fixed.
