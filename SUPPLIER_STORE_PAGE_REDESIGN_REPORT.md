## 3. How the three-section switcher was implemented
A `Tabs`/`TabsList`/`TabsTrigger` control (`value={section} onValueChange={...}`) — the same pattern already used throughout the Admin interface (e.g. `admin/delivery-page.tsx`, `admin/users-page.tsx`) — wrapped in an `overflow-x-auto [&::-webkit-scrollbar]:hidden` container so it scrolls horizontally rather than overflowing on narrow screens. `section` is local component state (`"details" | "media" | "hours"`, default `"details"`); switching it only changes which `Card` renders below — it never clears or touches `form`, so unsaved edits in any section survive switching away and back, and no query is triggered by the switch itself.

## 4. How the existing Store Preview was preserved and synchronized
The preview block (cover media, logo overlap, name, meta row, description, closed badge, music indicator) is untouched in structure and sits above the switcher, always rendered regardless of `section`. It already read exclusively from `form` (never from a separate "preview state"), so it was already live by construction — this redesign preserved that and did not change it. The only risk the three-section split introduced was **not** to the preview itself but to `form` as a whole: naively re-seeding the entire `form` from the server after every section's save (the original single-save page's behavior) would let saving one section silently discard unsaved edits sitting in the *other two* sections. This was addressed with a `seededRef` guard: the full `setForm(...)` sync from the fetched `store` now runs **once**, the first time the query resolves, never again on a subsequent refetch triggered by any section's own save — each save mutation instead only updates the specific fields it just persisted (or nothing at all, for Details/Hours, since the payload sent was already built from `form` and therefore already matches it). The preview keeps reading `form` the whole time, so it still updates immediately on every keystroke in any section, exactly as before — just without the cross-section data-loss risk.

## 5. How each section saves its data
Three independent `useMutation`s, each calling the **same, unmodified** `PUT /api/supplier/store` with only its own field subset:
- **Détails de la boutique**: `{ name, description, logoUrl, isOpen, visibility }`.
- **Médias d'arrière-plan**: `{ mediaType, coverUrl: cleanUrls[0] ?? form.coverUrl, coverUrls: cleanUrls, videoUrl, musicUrl }` (same empty-URL-filtering logic the original single save already did, now scoped to this section; its `onSuccess` also writes the server's cleaned `coverUrl`/`coverUrls` back into `form` so removed blank entries reflect immediately, without touching Détails/Horaires fields).
- **Horaires d'ouverture**: `{ openingHours: form.openingHours }`.

Because `upsertSupplierStore` already only sets whatever key is present in its input object (confirmed in §1), sending just one section's slice can never null out or revert the other two sections' already-saved values — no backend change was needed to make this safe. Each button has its own `disabled={saving}` guard (duplicate-submission prevention) and its own French success/error toast; a failed save leaves `form` exactly as the user left it (nothing resets on error), and the full-page `useEffect` re-seed no longer runs after the initial load, so a failed save can never be silently overwritten by a stale refetch either.

## 6. How the Opening Hours design reuses the Delivery Availability component's visual patterns
`account-availability-card.tsx`'s day-row markup was reproduced directly in Section 3 rather than imported as-is: same `w-16` pill-style day-toggle button (`bg-primary`/`shadow-sm` when open vs. `bg-muted` when closed — using `bg-primary` instead of that component's parametrized `accentClassName`, since the Supplier Store has no established accent color of its own to plug in), the same `Fermé` text swap when closed, the same paired `type="time"` inputs with a `–` separator when open, and the same separated, `bg-muted/40` "Résumé" summary `Card` below the editor, listing each day's `label : open – close` or `Fermé` — all driven by the exact same `form.openingHours` state Section 1-3's own inputs write to, so the summary updates on every change with no extra request. The one piece deliberately **not** reused is the reference component's `isOnVacation`/`onChangeVacation`/vacation-mode block — that concept belongs to Driver/Delivery-Company dispatch availability and has no Store equivalent, and the task explicitly forbade introducing it here. `WEEKLY_DAY_DEFS` (the shared French day-label list, already used by `supplierStores.openingHours`'s own type) was imported directly, replacing the page's previous hand-rolled English `DAYS` constant — one less duplicate day-list in the codebase, not a new one.

## 7. French localization coverage
Every visible string on the page was translated, matching the task's exact requested wording: page title ("Ma boutique") and subtitle, the approval badge's four states, the three section titles and their "Enregistrer" buttons, every field label/placeholder/helper text in all three sections (including the exact sentences specified: "Indiquez si votre boutique accepte actuellement les commandes.", "Masquez votre boutique sans affecter vos produits.", "Ajoutez jusqu'à 5 images. Elles défilent automatiquement sous forme de diaporama.", "La musique est diffusée automatiquement lorsque les propriétaires de cafés visitent votre boutique. Elle concerne uniquement votre boutique."), every toast (success and error), the "Fermée"/"Musique"/"produits"/"Distance affichée aux cafés à proximité" preview labels, and the schedule summary. The one place French coverage required a structural change rather than a string edit: the info-icon modal on the preview previously opened `store-detail-page.tsx`'s exported `InfoModal`, which that file's own comment says is deliberately English (it's the Coffee-Owner-facing page's wrapper). Rather than translating that shared, unrelated page's component, this page now calls the lower-level `AvailabilityModal` it wraps directly — which already defaults to French (confirmed by its own header comment naming "Supplier (store)" as an existing French caller) — so the modal is now in French without touching `store-detail-page.tsx` at all.

## 8. Database/API changes
None. No new column, no migration, no change to `PUT /api/supplier/store`'s accepted fields or to `upsertSupplierStore`'s logic — every field this page sends (`name`, `description`, `logoUrl`, `isOpen`, `visibility`, `mediaType`, `coverUrl`, `coverUrls`, `videoUrl`, `musicUrl`, `openingHours`) was already accepted by the existing endpoint before this task; the redesign only changed *how many of them* are sent in a given request (one section's worth instead of always all of them).

- If a brand-new Supplier (no store row yet) saves the Médias or Horaires section *before* ever saving Détails, the existing `upsertSupplierStore` insert branch will create the row with `name: ''` (its own pre-existing default for a missing name) rather than leaving the row absent — this is pre-existing behavior in `upsertSupplierStore`, unchanged by this task, but is a new *reachable* path now that sections can be saved independently and out of order; flagging it rather than leaving it undiscovered, though it does not crash or lose data (the Détails fields simply stay at their defaults until that section is saved too).
