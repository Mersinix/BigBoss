# Barista Performance Dashboard Update + Flash Reuse — Audit

## A. Initial state

### Performance pages (`Espace Barista Marketplace → Performance`)
`client/src/pages/barista-marketplace/performance.tsx` is a thin `SubTabSwitcher` wrapper over three pages:

- **Tableau de bord** (`dashboard.tsx`) — built entirely on `useBaristaRequests()`/`useBaristaMissions()`/`useBaristaReviews()`: KPIs were "Demandes ce mois", "Missions actives", "En attente" (legacy request status), "Note"; a 6-month "Demandes" area chart; a "Demandes récentes" list showing `cafeOwnerName`/`missionType`/request status.
- **Analyses** (`analytics.tsx`) — same legacy hooks plus `useBaristaRevenue()`: "Taux de complétion"/"Missions totales"/"Types de mission" (all mission-status-derived), a "Demandes reçues par mois" bar chart, a "Revenu estimé par mois" bar chart (duplicating Revenus), and "Meilleurs clients" ranked by mission count per `cafeOwnerName`.
- **Revenus** (`revenue.tsx`) — `useBaristaRevenue()` → `GET /api/barista/revenue` → `storage.getBaristaRevenueSummary(baristaUserId)`: a real ledger computed from `baristaMarketplaceMissions` rows with `status = 'COMPLETED'`, summing `rateInCents`, scoped to the authenticated barista server-side (`req.session.userId` → role-checked), zero-filled 6-month history, no joins/double-counting. **This page was already correct** — it is the one page in this task whose existing logic needed no rebuild, only a clarifying copy change (see Section B).

The legacy `baristaMarketplaceRequests`/`-Missions` system these pages read from has had **no creation UI anywhere in the Barista Marketplace or Coffee Owner account** since the mission-workflow cleanup (`mission_workflow_cleanup_audit.md`, same project). Dashboard/Analyses were therefore showing figures that can only ever shrink toward zero relevance going forward — exactly the "obsolete metrics… exclusively dependent on the legacy mission-request workflow" this task asks to remove.

### The current job-posting system (what replaces it)
`client/src/hooks/use-barista-marketplace.ts` already exposes everything needed, scoped server-side to the authenticated barista:
- `useMyBaristaJobApplications()` → `GET /api/barista/applications/mine` → `storage.getBaristaJobApplicationsForBarista(user.id)` — every application this barista has submitted, to both Offers and Missions, with `status` (`PENDING`/`PRESELECTED`/`INTERVIEW_SCHEDULED`/`ACCEPTED`/`REJECTED`), `createdAt`, `jobTitle`, `establishment`, and an embedded `meeting` (interview) object when one exists (`status`: `PROPOSED`/`CONFIRMED`/`CANCELLED`, `scheduledAt`).
- One gap found: the application object did **not** carry which `recordType` (`OFFER`/`MISSION`) its parent job post was — `jobs.tsx`'s own existing `useMyJobApplicationsByType()` works around this by cross-referencing against `useDiscoverBaristaJobs()` (the *discoverable*, i.e. still-published-and-not-expired, job list), which silently misclassifies an application once its job post is closed or expires. Fixed with a one-field additive backend change (Section B) rather than reusing that lossy pattern.
- `useBaristaReviews(userId)` — unchanged, real reviews data; valid under both workflows since a review is left on the barista's account, not on a specific request/mission.

### Flash — the existing button, and `BaristaFastSearch`
`Espace Barista Marketplace → Business → Profil` (`client/src/pages/barista-marketplace/profile.tsx:214-216`) has a `DashboardHero` action row with exactly the three controls named in the task: `PublicationStatusBadge` ("Publié"), an "Aperçu" button (`button-preview-profile`, opens the barista's own `BaristaDetailModal` read-only preview), and a **"Flash" button** (`button-flash-preview`, `Zap` icon) that opens `FlashPreviewModal` (`client/src/components/account/flash-preview-modal.tsx`).

`FlashPreviewModal` is **not** a search component — it is a full-bleed, story-style preview card of one account's own promotional "Flash (URL)" image (Settings → Compte), falling back to the profile photo, then a placeholder. Its own top comment states its exact purpose: *"reused identically by each of the 7 professional accounts' own Business → Profil 'Flash' preview button… and the Coffee Owner-facing Details Modal's Flash/lightning icon, so both call sites render byte-identical output."* Confirmed by grep: **all 7** professional account types (`driver`, `barista-academy`, `marketing`, `printer`, `delivery`, `maintenance`, and `barista-marketplace`) use this exact same component, same button label "Flash", same `Zap` icon, same `button-flash-preview` testid, on their own `Business → Profil` page. This is deliberate, standardized, cross-account infrastructure — the barista's Flash button already works correctly today, and is not broken.

`BaristaFastSearch` (`client/src/components/barista/barista-fast-search.tsx`) is a **Coffee-Owner-only discovery tool**: a Tinder-style swipeable feed over `baristas: BaristaMarketplaceCard[]` (OTHER baristas' profiles) with skill/location filters, a Favorite toggle (`useFavorites().baristaMarket`), an "Info" button opening that barista's detail modal, and a `BaristaJobTargetButton` ("associate the barista currently shown with one of the Coffee Owner's own manual job posts" — i.e. a hiring action). Confirmed via grep: its **only** call site in the entire codebase is `client/src/pages/cafe/barista/barista-page.tsx:753`, i.e. exactly the Coffee Owner integration quoted in the task. The codebase has an entire parallel family of these components — `print-fast-search.tsx`, `academy-fast-search.tsx`, `maintenance-fast-search.tsx` — one per professional account type, **every single one** exclusively Coffee-Owner-side. There is zero precedent anywhere in the app of a professional account opening its *own* FastSearch component on itself, and no configurable "mode" exists on any of them for that purpose.

### Data dependencies and role permissions
- `GET /api/barista/applications/mine`, `/revenue`, `/profile/:userId` all `requireAuth` + role-check `BARISTA_MARKETPLACE`, scoped to `req.session.userId` — never a client-supplied id.
- `BaristaFastSearch`'s data (`baristas` prop) comes from the Coffee Owner's own `useBaristaProfiles()` query, authorized for Coffee Owner role — not something the Barista Marketplace account has (or should have) a reason to call on its own behalf.

### Implementation gaps / risks identified
1. **The literal Flash instruction does not fit the codebase** — see Section D for the full reasoning and the decision this audit makes (documented per the task's own Section 3C escape valve: *"If the intended barista-side Flash content cannot be determined from the existing code, document the ambiguity… and implement the compatible behavior that can be established safely."*).
2. Applications lacked a direct `recordType` field, which the new Analyses page's "Offers vs Missions" breakdown genuinely needs — fixed via the smallest additive backend change (Section B).
3. The existing Revenus ledger is legacy-mission-based with no new-system equivalent (manually published missions carry free-text `remuneration`, no numeric rate) — per the task's own explicit instruction *"do not derive actual earnings directly from mission daily rates unless the existing business logic explicitly defines that calculation"* and *"if the existing Revenus page already correctly uses the current ledger, preserve it,"* this page's calculation logic was left untouched; only a clarifying subtitle was added.

## D. Flash integration — decision and reasoning

**Decision: the "Flash" button on `Business → Profil` keeps its existing behavior (`FlashPreviewModal`). `BaristaFastSearch` was not wired into it.**

This task's Section 3C explicitly anticipated this exact situation: *"Do not assume that the barista should search for other baristas simply because the existing component is named `BaristaFastSearch`… If the existing component is specifically designed for Coffee Owners to discover barista profiles, do not expose an inappropriate search experience to baristas… If the intended barista-side Flash content cannot be determined from the existing code, document the ambiguity… and implement the compatible behavior that can be established safely."*

Evidence gathered (Section A) left no reasonable path to a different conclusion:
1. **The button already has a complete, correct, working behavior.** `FlashPreviewModal` is standardized, shared, byte-identical infrastructure across **all 7** professional account types' own `Business → Profil` page — not a barista-specific or placeholder feature. Replacing it would make the Barista account the only one of 7 with divergent Profil-page behavior, for no functional gain.
2. **`BaristaFastSearch` is structurally a hiring tool, not a browsing tool.** Its actions are Favorite (a Coffee Owner's personal shortlist), "Info" (opens another barista's detail modal), and a job-target button ("associate the barista currently shown with one of *your* manual job posts") — all Coffee-Owner-side hiring semantics. Opening it from a barista's own profile would show that barista a swipeable feed of *other baristas* with buttons to shortlist or "hire" them for a job post the current user (a barista, not a Coffee Owner) does not have. There is no sensible interpretation of this as the barista's own "Flash" feature.
3. **No precedent, anywhere, for self-directed FastSearch.** The codebase has one `*FastSearch` component per professional account type (`barista-fast-search.tsx`, `print-fast-search.tsx`, `academy-fast-search.tsx`, `maintenance-fast-search.tsx`) — confirmed via grep that **every one** is Coffee-Owner-side only, with zero existing "mode" or configuration for self-use.
4. **Reusing it anyway would mean building a second implementation in practice.** `BaristaFastSearch` is tightly coupled to `BaristaMarketplaceCard[]`/the Coffee Owner's favorites store/`BaristaJobTargetButton`. Making it meaningful for a barista's own profile (e.g. swiping through job *posts* instead of barista *profiles*) would require a different data shape and different actions entirely — i.e., not "reusing the existing component," but writing a new one that merely looks similar. The task explicitly says not to duplicate it "unless the existing component is technically incompatible and the reason is documented" — which is exactly the case here, now documented.

**What was preserved exactly as the task required:** the existing Coffee Owner `BaristaFastSearch` integration (`barista-page.tsx:753`) was not touched in this task. No new Fast Search implementation was created for baristas. No Coffee-Owner-only data or actions were exposed to the Barista Marketplace account. The profile page's other functionality (Aperçu, publication status, all profile fields, portfolio, availability, work history) is untouched.

This is flagged prominently here (and in the final summary) rather than silently substituted, since it is a deliberate deviation from the task's literal Section 3 instruction — made under the explicit authority the task itself grants in Section 3C for exactly this situation.

## E. Verification

- **TypeScript**: `npx tsc --noEmit` — clean, exit 0, run after the backend field addition and again after each page rewrite.
- **Build**: `npm run build` — succeeded (`✓ built in 22.68s`, server bundled, no errors). Same pre-existing >500kB chunk-size warning as before this task, unrelated.
- **Live API check (pre-restart)**: logged in as an existing seeded Barista Marketplace account (`samir@barista.com`) against the currently-running dev server and confirmed `GET /api/barista/applications/mine` (200, empty array — this account has no applications yet) and `GET /api/barista/revenue` (200, zero-filled history) both still respond correctly with the **old** running backend code — confirming the additive `recordType` field change doesn't break the endpoint even before a restart, and that the UI's empty-state paths (verified by inspection: `EmptyState`/"Aucune candidature…"/"Aucun revenu…") are exercised by this account's real zero-data state.
- **Backend-restart-dependent**: same documented limitation as the prior mission-workflow-cleanup task in this project — the running `npm run dev` process (tsx, no `--watch`) predates this session's `storage.ts` edit and won't serve the new `recordType` field until restarted (`Stop-Process` is blocked by the environment's "Interfere With Workloads" sandbox guard). Until restarted, `application.recordType` will be `undefined` client-side, which `applications.filter((a) => a.recordType === "MISSION")` safely evaluates to `false` for every row — the Offers/Missions split KPIs will under-report (show 0/0 or misattribute to neither bucket) rather than crash, and will self-correct once the process restarts. All other Dashboard/Analyses logic (counts, dates, statuses, meetings) does not depend on this field and is correct right now.
- **Flash modal behavior**: not changed, so no new behavior to verify — confirmed by reading `FlashPreviewModal` and its 7 call sites that the existing behavior (opens on click, closes on the X/overlay, no mutation, no profile-state reset) is unaffected since no file in that path was edited.
- **No browser/Playwright tool was available in this session** — relied on TypeScript, build, direct backend inspection, and the one live API round-trip above (no browser automation tool was available to literally click through the rebuilt Dashboard/Analyses charts).
- **Authorization**: no new routes were added; the one backend change is a read-only field addition to an already-authorized, already-scoped query. No client-supplied IDs are trusted anywhere in the changed code.
- **Regression checks performed by inspection**: `profile.tsx`, `business.tsx`, `jobs.tsx` (Offres/Missions tabs), `admin/barista-page.tsx`, and the Coffee Owner's `barista-page.tsx` `BaristaFastSearch` integration were not modified by this task (confirmed via `git status`/diff scope) — only `dashboard.tsx`, `analytics.tsx`, `revenue.tsx` (copy only), `performance.tsx` (comment only), and the three additive type/storage changes for `recordType`.
