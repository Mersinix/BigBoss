# Maintenance Interventions — Implementation Audit

## 1. Root cause / initial finding

There is **no job-posting system at all for Maintenance today** — confirmed by reading every Maintenance-related table in `shared/schema.ts`. The only existing Coffee-Owner → Maintenance-provider interaction is `maintenanceReservations`: a single-provider-only reservation (`maintenanceUserId` always one specific provider, chosen by opening that provider's own `AgentDetailModal` and clicking "Réserver"). There is no concept of:
- publishing a request to a pool of eligible providers,
- manually targeting several specific providers for one request,
- providers applying/responding to a listing,
- "my published interventions" management separate from "my reservations."

This is a genuine greenfield feature for Maintenance, to be built by porting the **Barista job-posting system** (`baristaJobPosts`/`baristaJobTargets`/`baristaJobApplications`/`baristaJobMeetings`, hero "Offre" button, `JobManagementModal`/`JobPostFormModal`/`BaristaJobTargetButton`), which already solves exactly this shape of problem for Barista.

## 2. Barista reference workflow (full trace)

- **Hero button**: `client/src/pages/cafe/barista/barista-page.tsx:526-536` — a `Briefcase`-icon `w-8 h-8 rounded-full` button, `canAct`-gated only (not Admin-toggleable, unlike Fast Search/Report), opens `JobManagementModal`.
- **Creation form**: `client/src/components/barista/job-post-form-modal.tsx` — manual (non-zod) client validation (`titleError`, `dateError`), submits via `useCreateBaristaJob()`/`useUpdateBaristaJob()` → `POST/PATCH /api/barista/jobs[/:id]`. Establishment/location prefill from `user.name`/`user.locationAddress` only on create. Two submit buttons (`Enregistrer comme brouillon` → status `DRAFT`, `Publier` → status `PUBLISHED`).
- **Publication mode**: `baristaJobPublicationModeEnum = ['AUTOMATIC','MANUAL']` (pg enum). **Manual targeting is a join table** (`baristaJobTargets: {jobPostId, baristaUserId}`, unique pair), **not** an array column, **not** a Fast-Search "multi-select" UI. Targeting happens *after* the job exists, one provider at a time, via a single shared dropdown component (`BaristaJobTargetButton`) mounted both inside `BaristaFastSearch`'s action rail and inside `BaristaDetailModal`'s icon row — both just pass `{baristaUserId, baristaName}` and the button lists the owner's own `MANUAL+PUBLISHED` jobs to associate with. The DB's unique `(jobPostId, baristaUserId)` index makes re-targeting idempotent — no app-level dedup needed.
- **Backend derivation of ownership**: `POST /api/barista/jobs` always sets `cafeOwnerId` from `req.session.userId` (`requireApprovedCafeOwner` middleware); `storage.createBaristaJobPost`/`updateBaristaJobPost` additionally strip any client-sent `cafeOwnerId`/`id`/timestamps before writing — defense in depth.
- **Visibility/eligibility** (`storage.getDiscoverableBaristaJobPosts`): union of (a) every `AUTOMATIC + PUBLISHED + not-expired` job, shown to **every** session user with role `BARISTA_MARKETPLACE` (no profile-approval/visibility re-check at read time beyond the role check itself), and (b) `MANUAL + PUBLISHED + not-expired` jobs where a `baristaJobTargets` row exists for this specific barista. Every list/detail/apply route **re-derives** this server-side — the client is never trusted to have only shown eligible jobs.
- **Applications**: one row per `(jobPostId, baristaUserId)` (unique pair ⇒ duplicate-prevention is the DB index, with a route-level pre-check plus a duplicate-key catch as belt-and-suspenders). Status: `PENDING → {PRESELECTED,ACCEPTED,REJECTED}`, `PRESELECTED/INTERVIEW_SCHEDULED → {ACCEPTED,REJECTED}` — owner-driven; `INTERVIEW_SCHEDULED` is a side-effect of proposing a meeting. A separate `baristaJobMeetings` table (1:1 with an application) handles interview scheduling, confirmable/cancellable by **either** party.
- **My Account**: `client/src/components/cafe/barista-offres-list.tsx` (`BaristaOffresList`) — a pure read list (`useMyBaristaJobs(recordType)`), mounted inside `marketplace-layout.tsx`'s existing Barista reservations tab, alongside a local Missions/Offres pill switcher. Clicking a row opens the same `JobManagementModal` deep-linked by id.
- **Notifications**: `notify()` (persistent, dedupe-keyed, pref-gated by `prefKey:"barista_jobs"`) + `broadcast`/`broadcastToUsers` (`"barista_jobs_updated"`, a pure refetch signal) at every state change: job created/updated, provider targeted, application received, application status changed, meeting proposed/updated.
- **Query invalidation**: one shared `invalidateBaristaJobs(qc)` helper, prefix-invalidating `["/api/barista/jobs"]` + `["/api/barista/applications/mine"]` after every mutation — this is what keeps the owner's "mine" list, the owner's detail view, the barista's "discover" list and the barista's "my applications" list all in sync without bespoke per-view invalidation.

## 3. Existing Maintenance reservation workflow (what must be preserved)

- `maintenanceReservations` (`shared/schema.ts:2183-2205`): one row always targets exactly one `maintenanceUserId`; `status` is plain `text` (not a pg enum) with vocabulary `PENDING/CONFIRMED/COMPLETED/CANCELLED/RESCHEDULED/RESCHEDULE_PENDING`; `urgency` is plain `text` with vocabulary `LOW/NORMAL/HIGH/URGENT`.
- Creation: `POST /api/maintenance/reservations` (`server/routes.ts:903-972`) — Coffee-Owner-only, validates the named provider's availability/category/weekly-hours, derives `cafeOwnerId` from session, calls `storage.createMaintenanceReservation`, then `refreshMaintenanceMessagingState`, `broadcast`/`broadcastToUsers("maintenance_reservation_updated"/"conversation_updated")`, and two `notify()` calls (`prefKey:"maintenance_requests"` to the provider, `prefKey:"maintenance_status"` to the owner).
- Provider-side lifecycle: `client/src/pages/maintenance/planning.tsx` — `PATCH /api/maintenance/reservations/:id/status` (`PENDING→CONFIRMED→COMPLETED`, or `→CANCELLED`, or `→RESCHEDULE_PENDING`), `PATCH .../reschedule-response` (owner accepts/rejects a reschedule proposal).
- Coffee-Owner-facing history: `client/src/components/cafe/marketplace-layout.tsx:166-169,197-203,243-786,1048-1090` — the Maintenance tab of the shared "Réservations" panel inside My Account; reads the **same** `GET /api/maintenance/reservations` endpoint, role-branched server-side.
- Provider eligibility/visibility gate (reused verbatim for the new feature): `storage.getMaintenanceProfiles` (`server/storage.ts:5846-5860`) — `users.role='MAINTENANCE' AND users.status='approved' AND maintenanceProfiles.{marketplaceVisible:true, isOnVacation:false, isFrozen:false, publicationStatus:'APPROVED'}`.
- The Details modal (`AgentDetailModal`, same file, lines 283-517) currently has a bottom-right icon row (Signaler/Disponibilité/Avis/**Flash**) using the `w-9 h-9 rounded-full bg-black/40 backdrop-blur-sm ...` convention. **Flash** (lines 445-447) only opens a `<FlashPreviewModal>` showing `agent.flashImageUrl` — a pure image viewer, fully isolated (its own `flashModalOpen` state, nothing else references it). Safe to replace in place.
- `MaintenanceFastSearch` (`client/src/components/maintenance/maintenance-fast-search.tsx`) has **no selection mode at all** — it is a single-card swiper with a 3-icon action rail (Filter / Info / Favorite). The `Info` button's `onOpenDetail(current)` callback is the hook point for any new per-provider action (mirrors Barista's `BaristaJobTargetButton` mount point).
- Nested-modal-safe pattern (already fixed in a prior task, must not regress): `fastSearchOpen`/`detailOpen` are independent `useState`s in `maintenance-page.tsx`; `MaintenanceFastSearch` is mounted before `AgentDetailModal` in JSX (DOM-order stacking, since this app's `Dialog` uses a fixed `z-50`); `onOpenDetail` never calls `setFastSearchOpen(false)`. Any new modal added to this flow must follow the same rule: its own independent boolean, mounted last if it can coexist with the other two, and its own close only ever touches its own state.

## 4. Maintenance-specific data model (mirrors Barista, simplified where safe)

Ported 1:1 except: **no OFFER/MISSION record-type split** (interventions are one kind of listing) and **no meeting/interview sub-system** (an intervention isn't a hiring process — once the Coffee Owner accepts a provider's response, that response is linked to a real `maintenanceReservations` row, reusing the entire existing reservation lifecycle/UI instead of inventing a parallel "in progress/completed" state machine). This directly satisfies the task's "do not create duplicate reservation systems" and "do not misrepresent a reservation as an intervention publication" requirements: an intervention **post** (the listing) and a **reservation** (the actual scheduled job) stay two distinct, separately-displayed records, linked by `maintenanceJobApplications.reservationId` only once a response is accepted.

New tables (`shared/schema.ts`):
- `maintenanceJobPublicationModeEnum`: `['AUTOMATIC','MANUAL']` (same values as Barista).
- `maintenanceJobStatusEnum`: `['DRAFT','PUBLISHED','CLOSED']` (same values as Barista — drafts are safely supported since the form/backend mirror Barista's exact DRAFT/PUBLISHED/CLOSED handling byte-for-byte).
- `maintenanceJobApplicationStatusEnum`: `['PENDING','ACCEPTED','REJECTED']` (simplified from Barista's 5-state set — no PRESELECTED/INTERVIEW_SCHEDULED, since there's no interview step for a repair job).
- `maintenanceJobPosts`: `id, cafeOwnerId, title, establishment, locationAddress, categories (text[]), urgency (text, LOW/NORMAL/HIGH/URGENT — same vocabulary as maintenanceReservations.urgency), description, requirements, contactPhone, scheduledDate (text, "YYYY-MM-DD"), scheduledTime (text, "HH:MM"), expiresAt (timestamp), publicationMode, status, createdAt, updatedAt`.
- `maintenanceJobTargets`: `id, jobPostId, maintenanceUserId, createdAt` — unique `(jobPostId, maintenanceUserId)`, exact mirror of `baristaJobTargets`.
- `maintenanceJobApplications`: `id, jobPostId, maintenanceUserId, message, status, reservationId (nullable, set on ACCEPTED), createdAt, updatedAt` — unique `(jobPostId, maintenanceUserId)`.
- Computed types `MaintenanceJobPostWithStats` (`totalApplications/pendingApplications/acceptedApplications/rejectedApplications/targetCount`) and `MaintenanceJobApplicationWithParties` (`maintenanceName/maintenanceProfileImageUrl/jobTitle/establishment`), mirroring Barista's stats-attachment pattern.

Field mapping from the task's required form fields to this model: Intitulé→`title`, Établissement→`establishment` (prefilled from `user.name`, same as Barista), Localisation/adresse→`locationAddress` (prefilled from `user.locationAddress`), Date et heure→`scheduledDate`+`scheduledTime` (distinct from `expiresAt`, which is the *application deadline* — mirrors Barista's own `expiresAt` vs. `missionStartDate` distinction, called out explicitly in the task), Catégorie→`categories` (multi-select chips sourced from the real `maintenanceCompetencies` Admin taxonomy, the same taxonomy `maintenanceProfiles.categories`/`skills` already use as free text), Urgence→`urgency` (reusing `maintenanceReservations.urgency`'s exact LOW/NORMAL/HIGH/URGENT vocabulary — no incompatible new values), Description→`description`, Exigences→`requirements`, Mode de publication→`publicationMode`. Additional fields reused from the existing reservation form: `contactPhone` (prefilled from `user.phone`, mirrors the reservation modal exactly).

**Eligibility decision (explicit, deliberate choice)**: like Barista, `categories` on the job post are **displayed criteria**, not a server-side filter for AUTOMATIC-mode discovery — an eligible provider decides for themself whether to respond based on the listed categories/urgency/description, exactly as a Barista decides from the listed employment type/education/languages. What the server *does* enforce for every Maintenance provider who can see/apply to an AUTOMATIC-mode job is the same gate the public marketplace already uses (`users.role='MAINTENANCE' AND status='approved' AND marketplaceVisible AND !isOnVacation AND !isFrozen AND publicationStatus='APPROVED'`) — stricter than Barista's reference (which only checks the session role), directly satisfying this task's explicit instruction that ineligible/unapproved/suspended providers must never see a published intervention.

## 6. Automatic vs. manual publication — implementation

- **Automatic**: on `PUBLISHED` + `AUTOMATIC`, `storage.getDiscoverableMaintenanceJobPosts(maintenanceUserId)` returns it to every session user that is both role `MAINTENANCE` and passes `isMaintenanceProviderEligible` (Section 4) — re-checked on every list/detail/apply call, never cached client-side as a trust boundary.
- **Manual**: on `PUBLISHED` + `MANUAL`, only visible to providers with a `maintenanceJobTargets` row for that job, added via `MaintenanceJobTargetButton` (mounted in both Fast Search and the Details modal, exactly like Barista). The POST `/targets` route validates: the job belongs to the session owner, the job is actually `MANUAL`, and the target user is role `MAINTENANCE` **and** passes `isMaintenanceProviderEligible` (stricter than Barista's reference, which only checks the role) — satisfying "confirm that manually selected providers are eligible."
- Switching publication mode is a plain field on the same `PATCH /api/maintenance/jobs/:id` — never silently defaulted; the form always reflects whichever mode is currently selected and only changes on explicit user action, so a manually-targeted intervention is never silently switched to automatic.

## 7. Provider-side visibility and response workflow

New page `client/src/pages/maintenance/interventions.tsx`, reached from a new "Interventions" tab in the Maintenance professional's own account shell (alongside Profil/Planning). Discover list (`GET /api/maintenance/jobs/discover`) shows a "ciblée" badge for manually-targeted rows (mirrors Barista's `isTargeted`); Apply dialog posts a short message (`POST /api/maintenance/jobs/:id/apply`), re-validated server-side for eligibility/expiry/duplicate exactly like Barista. A "Mes candidatures" list (`GET /api/maintenance/applications/mine`) shows PENDING/ACCEPTED/REJECTED; once ACCEPTED, the application links to the real reservation (`reservationId`), which the provider already sees and manages via the existing, unmodified `planning.tsx` reservation lifecycle (Confirm/Reprogrammer/Terminer).

## 8. My Account integration and lifecycle

Coffee-Owner-facing: a new "Interventions" pill inside the existing Maintenance tab of the shared Réservations panel (`marketplace-layout.tsx`), listing the owner's own job posts (title, establishment, mode badge, status badge, response count, expiry, scheduled date) exactly like `BaristaOffresList`. Clicking a row (or "Publier une intervention") opens `MaintenanceJobManagementModal`, which shows targeted profiles (manual mode) and every application with Accepter/Rejeter actions. **Accepting** an application (`PATCH /api/maintenance/applications/:id/status {status:"ACCEPTED"}`) creates a real `maintenanceReservations` row via the existing `storage.createMaintenanceReservation` (same fields: category from the job's first selected category, urgency/location/description/contactPhone from the job, date/time from `scheduledDate`/`scheduledTime`, `status:"PENDING"`), links it via `application.reservationId`, and fires the same `notify`/`broadcast` calls the existing reservation-creation route already fires — so the brand-new reservation appears instantly in both the owner's and the provider's existing, **completely unmodified** Réservations/Planning views. The existing "Réservations" pill and all of its historical rows are untouched — an intervention post and a reservation are always two distinct, separately-displayed records, linked only by this one optional `reservationId` field.

Status lifecycle implemented (deliberately smaller than the task's full candidate list, per its own "implement only what is needed" instruction): `DRAFT → PUBLISHED → CLOSED` for the post itself (owner-driven, identical to Barista); `PENDING → ACCEPTED/REJECTED` for an application (owner-driven). "In progress"/"Completed" are **not** duplicated at the application level — once ACCEPTED, the linked reservation's own existing status machine (`PENDING→CONFIRMED→COMPLETED`, provider-driven) is the single source of truth for execution status, avoiding exactly the two-systems-disagreeing risk the task warns about.

## 9. Authorization and security checks

- Every mutating route uses `requireApprovedCafeOwner` (job create/update/target/accept-reject) or an inline `role==='MAINTENANCE'` + eligibility check (discover/apply) — never a client-supplied owner/provider id for *authorization* purposes (a provider id is accepted as a *request body value* only where the route's own job is to validate it, e.g. `/targets`).
- Ownership of a job post is re-checked on every owner-only route (`existing.cafeOwnerId !== req.session.userId → 404`, never 403, to avoid leaking existence — mirrors Barista exactly).
- `storage.createMaintenanceJobPost`/`updateMaintenanceJobPost` strip any client-sent `cafeOwnerId`/`id`/timestamps before writing, mirroring Barista's defense-in-depth.
- Manual-mode visibility is enforced server-side on every read (`GET /api/maintenance/jobs/:id`, `/discover`, `/apply`) — a non-targeted provider guessing a job id gets 404/403, never the job's content.
- Duplicate applications are prevented by the DB's unique `(jobPostId, maintenanceUserId)` index (same belt-and-suspenders pattern as Barista: a pre-check plus a duplicate-key catch).
- Accepting an application creates the reservation and updates the application status in the same request — not two separate client round-trips that could leave inconsistent state on a failure between them.
