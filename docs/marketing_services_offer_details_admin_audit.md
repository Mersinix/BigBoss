# Marketing Services Management, Offer Details & Admin Synchronization — Audit

## A. Existing architecture (audited before any change)

- **Model**: `marketingServices` (`shared/schema.ts`) — `id`, `marketingUserId`, `title` (added in the previous task), `category`, `startingPriceInCents`, `responseTime`, `description`, `imageUrl`, `isPublished`, timestamps. No "Offer details" field.
- **API**: one shared `marketingServiceInputSchema` (zod) backs both `POST /api/marketing/services` (create) and `PATCH /api/marketing/services/:id` (update); `storage.createMarketingService`/`updateMarketingService` both do a generic `{...safeData}` spread into the insert/update — adding a field to the zod schema is sufficient, no per-field allowlist to touch.
- **Read paths** (all plain `...service` spreads, confirmed): `getMarketingServicesForProvider` (the agency's own list — `GET /api/marketing/services/mine`), `getPublishedMarketingServices` (Coffee Owner `/marketing` — `GET /api/marketing/services`), `getMarketingServiceCard` (single-service detail — `GET /api/marketing/services/:id`, used by the Service Detail modal, Fast Search's detail hand-off, and Admin's own preview). A new field added to the table automatically flows through all three with zero code changes to `storage.ts`.
- **Espace Marketing → Business → Services** (`client/src/pages/marketing/services.tsx`): one `ServiceFormDialog` (Nouveau/Modifier, fields: Titre, Catégorie, Prix, Temps de réponse, Description, Image) + a card grid (`grid-cols-1 md:grid-cols-2`) using plain `shadcn Card`s with a text header, description, responseTime, price, a `Switch` (publish toggle), and three buttons (Aperçu/Modifier/Supprimer). All four actions are real: `useUpdateMarketingService`/`useDeleteMarketingService` mutations, a `window.confirm` before delete, and `MarketingServiceDetailModal` (`readOnly`) for Aperçu.
- **Coffee Owner `/marketing`**: mapped cards via the shared `MarketingMappedServiceCard` (built in a previous task) — image + agency-name/category/availability badges, title, description, price+avis row. Clicking opens `MarketingServiceDetailModal` (same component the agency's own Aperçu uses, `readOnly={false}` here) — hero image, title/category/provider-type badges, rating/location, a 2-column Price/Response-time grid, an "Agence" section, Message/Demander un devis actions. No Offer Details section exists yet.
- **Admin → Marketing** (`client/src/pages/admin/marketing-page.tsx`): one aggregate `GET /api/admin/marketing` overview (`storage.getMarketingAdminOverview`), client-side tabs (`Catégories de services` / `Comptes Marketing` / `Projets récents` — note: not yet in the order the task requires), `usePagination`/`DataPagination` already used on the Comptes/Projets tabs (the established, consistent pagination convention across every Admin page in this codebase — all client-side, over one already-fetched aggregate payload, never server-side pagination). **Crucially**, `getMarketingAdminOverview`'s `accounts` array **already embeds each agency's own real `services: MarketingService[]` array** (confirmed by reading the function — `servicesByAgency` built from one real `db.select().from(marketingServices)`, attached per account) — Admin already has full access to every real service row, just never surfaced as its own section. This means no new backend endpoint or duplicated dataset is needed for "Services Marketing" — it can be derived client-side from data Admin already fetches.
- **Admin dashboard stats** (`totalAccounts`, `activeAccounts`, `visibleAccounts`, project counts, `reviewCount`, `averageRating`, `totalRevenueCents`) — untouched by this task; no service count currently included there.

## B. Card redesign (Espace Marketing → Business → Services)
The management card was rebuilt to use the same visual language as `MarketingMappedServiceCard` (image container on top with badges, title → description → price/avis-style footer below), while keeping it a genuinely distinct component (not the shared read-only card) because it needs real management affordances the Coffee Owner card doesn't have:
- Image on top (`aspect-[4/3]`), category badge bottom-right (same taxonomy icon resolver), and a status dot bottom-left (green = `isPublished`, gray = draft — the same dot-indicator *language* as the Coffee Owner card's availability dot, deliberately repurposed here to mean "published" since that's this context's real, equivalent concept — not "agency availability", which belongs to a different settings page).
- No agency-name badge (redundant — this is the agency managing its own listing) and no Avis overlay (rating/review count is not part of this page's existing data fetch, `getMarketingServicesForProvider` returns plain service rows with no agency-level stats; fabricating or fetching it solely for cosmetic parity was judged out of scope for "the smallest safe change" — explicitly noted here rather than silently skipped).
- Below the image: Title, category text + Offer-details-aware description, the existing Prix de départ/Temps de réponse row, then the **unchanged** action row: Switch (publish/unpublish), Aperçu, Modifier, Supprimer — all wired to the exact same mutations/confirmation dialog as before.

## C. Existing actions — confirmed preserved
`Aperçu` (opens `MarketingServiceDetailModal` readOnly), `Modifier` (opens `ServiceFormDialog` pre-filled), `Supprimer` (same `window.confirm` + `useDeleteMarketingService`), and the publish `Switch` (`useUpdateMarketingService({isPublished})`) all keep their exact existing `onClick`/mutation wiring — only the surrounding card markup changed.

## D. Offer Details
- **Database/model**: `marketingServices.offerDetails` — `text("offer_details").notNull().default("")`, additive, same backward-compatible pattern as `title` (verified via `psql` that existing rows receive `''`, not fabricated content).
- **Create**: `Nouveau service` gained a "Détails de l'offre" `Textarea`, positioned after Description and before the Image field, optional, included in the create payload.
- **Edit**: `Modifier le service` loads the existing value (`service.offerDetails ?? ""`), lets the agency change it, and saves through the same `PATCH` call as every other field — no second storage mechanism.
- **Preview (Aperçu)**: unchanged entry point (`MarketingServiceDetailModal`, `readOnly`) — since that modal now renders Offer Details whenever present, Aperçu shows it automatically, using the real saved value, never a preview-only fake value.
- **API**: `offerDetails: z.string().max(4000).optional()` added to the one shared `marketingServiceInputSchema` used by both create and update routes — no new endpoint.
- **Coffee Owner Service Detail**: `MarketingServiceDetailModal` renders a new "Détails de l'offre" block (only when `service.offerDetails?.trim()` is non-empty — never a placeholder for services that don't have one), placed after the service description and before the Price/Response-time grid, per the requested hierarchy.

## E. Admin → Marketing — Services Marketing
- **Switcher reordered** to exactly: `Comptes Marketing`, `Services Marketing`, `Projets récents`, `Catégories de services` (previous order was `Catégories de services`, `Comptes Marketing`, `Projets récents` — the two existing tabs' content was not altered, only their position + the new one inserted).
- **Data source**: derived entirely client-side from the already-fetched `data.accounts` (each account's own `services` array, already real) via one `useMemo` that flattens every account's services into one list, each row carrying its parent agency's `name`/`profileType`/`marketplaceVisible`/`isAvailable`/`isOnVacation`/`isFrozen`/`status` alongside the service's own fields. No new API route.
- **Filters**: search (title/description/category/agency name), category (from the real `taxonomy`), agency (from the real distinct agency names present), status/visibility (Publié/Brouillon = `isPublished`), availability (agency `isAvailable && !isOnVacation`) — all built from real values already in the fetched data, no fake filter options.
- **Pagination**: the same `usePagination`/`DataPagination` pair already used by this page's Comptes/Projets tabs — client-side over the flattened list, matching the established, consistent convention across every Admin page in this codebase (none of which do server-side pagination).
- **Empty state**: same "no results" card pattern already used elsewhere on this page (icon + message + optional "clear filters" action).
- **Service details**: clicking a row opens the **existing** `MarketingServiceDetailModal` (`readOnly`) — already imported in this file — rather than a new Admin-only modal.

## F. Synchronization
All three contexts (Espace Marketing, Coffee Owner `/marketing`, Admin Services Marketing) read the same `marketingServices` rows through the same three storage functions (`getMarketingServicesForProvider`, `getPublishedMarketingServices`/`getMarketingAdminOverview`, `getMarketingServiceCard`), all of which spread the raw row — `title`/`category`/`description`/`offerDetails`/`imageUrl`/`startingPriceInCents`/`responseTime`/`isPublished` are identical by construction, never duplicated or recomputed independently.
